# Ashoka configuration authority — implementation progress

Core owns the setting catalogue and complete candidate validation. Scheduler, events and narrative use the same schemas at startup, runtime update and persistence. Zero throttles remain zero; non-finite numbers, negative rates, unknown changed keys and contradictory narrative intervals fail before mutation. All known literal source keys and role fields are inventoried with owners, units, constraints, source/default expressions and apply semantics in [configuration-inventory.json](configuration-inventory.json). `npm run config:check` detects source/catalogue drift. Client/build-only values have a named read-only exception.

Explicit deployment values captured before instance loading outrank persisted instance intent, followed by owner defaults. A dashboard save changes persisted intent; it cannot silently remove a deployment override. Inspection distinguishes saved values, actual runtime values, origin and mismatch. Unknown imported values survive and remain read-only/redacted. Instance identity and launcher paths cannot be changed through configuration apply. Role secret references remain separate from job policies.

Each daemon save uses the expected content revision and a payload-bound operation ID. A physical config-directory writer lease excludes another authority. Unique temporary files are flushed before atomic rename. A private `.engine-config/<file-identity>/<operation-hash>.json` stores the before/after backup and prepared/committed/aborted receipt. Recovery recognizes the actual file hash: before means aborted, after means committed, and any third state fails closed. A retry retrieves its own terminal receipt without another effect. Revision-aware undo rejects intervening edits. No graph, schedule definition or scan checkpoint is reset by a configuration operation.

Receipt files contain configuration secrets and are never graph resources, model context, API responses or logs. Files request POSIX mode `0600` and folders `0700`; Windows uses inherited directory ACLs. This is not a claim of Windows ACL hardening or power-loss qualification. Single-file rename and injected interruption/readback are tested; OS-specific durability qualification remains a release gate. Backups remain retained; automatic receipt pruning is not enabled.

The bounded engine.env v1 document marks JSON-quoted strings explicitly. Existing v0 quotes remain literal, preserving Windows backslashes. Save converts active values, preserves unrelated comments/values, removes duplicate active assignments, and writes explicit empty values when clearing a setting. Invalid existing values remain diagnosable; activation fails rather than substituting broad defaults or falling back to an unscoped instance.

The existing dashboard forms now save before hot application, carry a revision and operation ID, retain unrelated fields, and report failure instead of redirecting to success. Scheduler/events/narrative edits survive restart; old instance aliases are removed during those edits. Read-only deployment aliases still override them. Architect's daemon persistence uses the same authority. The synchronous utility functions remain standalone compatibility/scaffold writers without a daemon CAS promise.

The API is `GET /api/config/v1`, `/catalogue` and `/roles`; `POST /apply`, `/template/preview`, `/template/apply` and `/undo`. Apply requires `expected_revision`, `operation_id` and `updates`; null removes an instance override. Catalogue includes descriptive constraints, category and nonsecret default-template values; complete server validation remains mandatory. Roles show six requested/effective daemon policies and finite allocations, excluding Architect session overrides and secret values. Requests and documents are bounded to 1 MiB, with 16 KiB lines. All inspection and receipt responses omit secrets and raw backup contents. Apply refreshes cached model configuration and the live component owners; runtime activation failure is separate from the durable save. Replayed receipts never repeat activation. Removed instance overrides also show mismatches until the effective runtime reflects the deletion.

Template preview accepts only `default`, `ollama` or `lmstudio`, plus optional selected keys. It performs no writes or provider calls and returns a semantic diff, protected/unknown keys retained, expected revision and template hash. Apply binds that template hash and revision, preserves credentials, identity, repositories, authority and paid budgets, and retains a backup. Template/undo operations stage settings: runtime mismatch stays visible until activation/restart. No template grants full access, remote control or paid work. Computer Use route settings validate named profiles and finite action/image/time/retention bounds; default enablement is off and a separate execution grant remains required in Slice 31.

The `config.changed` in-process event carries a redacted committed receipt after durability. Clients must reread by revision after reconnect; this event is not durable notification delivery. Job/session admission, pinned configuration and HTTP authority are provided by Slices 11/17. The [compact settings/runtime workspace](configuration-workspace.md) in Slice 23 adds tabs, search, structured controls and protected template/readback workflows above this owner; its integrated qualification remains pending.
