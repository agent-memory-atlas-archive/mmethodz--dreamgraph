## C01 — One canonical contract with explicit owners

Core/daemon owns graph semantics and mutation authority. Extend `src/graph`, `src/types/index.ts`, `src/cognitive/types.ts` and the existing trust-state/evidence-ledger/lifecycle modules. Core generates versioned JSON schemas and SDK/schema artifacts for `packages/sdk`, host/client adapters and Python analytics. Architect, CLI, MCP, Explorer, analytics and plugins consume these contracts; they do not independently define graph identity, trust or lifecycle. MCP is an authority surface over core, not a second semantic owner. A process boundary is not the definition of the contract: any permitted embedded/offline read must use the same core semantics; it cannot become an independent writer.

The project maintainer is accountable for contract decisions and assigning implementers. Technical ownership is mapped in each slice. Core persistence reviews durable writes/migrations; cognitive trust ownership reviews promotion/evidence changes; daemon authority reviews permissions/sessions; each consumer owner signs its conformance evidence. These are responsibilities, not invented staff appointments. A single person may hold roles, but risky changes still require an explicit review record distinct from implementation claims.

Represent identity (instance, typed stable ID), provenance (source/human/model/validation process), trust/validation state, evidence ancestry/revision, freshness and confidence meaning separately. Display names do not identify records. Human assertion does not imply verification; source evidence does not imply permanent freshness. Candidate/model confidence, evidence strength and validation status must never share an unlabeled number. Narration, repetition, metacognition, model agreement and federation cannot create independent evidence from the same ancestor. On evidence change, retain history, mark affected claims for re-evaluation and surface contradictions. DreamGraph remains exploratory: useful unproven ideas stay available as hypotheses.

**DreamGraph guarantees system correctness under valid use. The user owns operating discipline outside that contract.** Valid use means a documented supported route/version, declared instance/project/scope and satisfied authority/configuration prerequisites. DreamGraph must enforce those prerequisites and correctly preserve identities, committed state, reconciliation, concurrency, budgets, lifecycle, evidence and truthful results; a bug cannot be dismissed as operator discipline. A failed worker, interrupted write, stale UI or invalid request must produce the specified recoverable/error state. The user chooses when to work outside DreamGraph, when substantial out-of-band changes warrant an inclusive scan, and which optional paid/cognitive workflows to run. Do not impose recurring scans, suspicion-driven warnings or extra approvals for work already authorized within that contract. Unsupported/out-of-scope activity has an explicit boundary; the product does not claim to have observed it.

**Old scan does not equal stale graph.** Managed MCP/Architect mutations keep affected knowledge current through reconciliation. Preserve current unaffected and reconciled knowledge even if only one full scan ever occurred. Freshness is relative to concrete evidence changes and committed scope coverage, not scan/enrichment age, raw Git dirty status or commits since scan. Known mismatches/withdrawals or unfinished reconciliation affect only their actual scope; missing history/mapping is separately unknown. Optional pending cognition does not make reconciled source facts stale. A missing old scan baseline may limit a scan operation, but does not invalidate later knowledge. The user chooses an inclusive scan after substantial work outside DreamGraph; do not infer such work from time alone. Explicit expiry for transient observations applies only to that evidence kind. See XS21 for the cross-surface regression specification.

Revision-7 publication ownership is precise: Slice 2 supplies the existing JSON journal/barrier publication primitive and canonical identity/snapshots; Slice 5 extends it with business effect/job/reconciliation receipts. Source/scan hashes, graph/domain revisions, publication sequence and process epoch are distinct. No mandatory database replacement or additional scheduler is introduced. The [execution simulation](execution-simulation.md) records all 35 concept paths, 32 slice handoffs and the accepted-ADR applicability/amendment register, including ADR-238/239/240. Review scoped amendments before affected activation; this planning pass accepts none.

## C02 — Bounded compatibility, forward migrations and retirement

Support the current and previous **schema major** for supported persisted/transport contract families. Product release numbers are independent; 13.4.0 is not automatically schema 13. Inventory the actual versions in Slice 0, and explicitly classify unversioned stores as legacy/unknown rather than guessing.

Current core reads current/previous-major records through adapters and writes the current canonical format. Prior-major clients receive negotiated compatible projections; mutations require an explicit lossless adapter or a visible upgrade-required error. No silent downgrade/drop of new semantics. Supported old client responses must not imply completeness where an adapter cannot preserve it. Independent schema families advertise their supported ranges and compatibility matrix; do not invent an unnecessary global version that forces all families to change together.

When major M is current, M-1 is supported; M-2 and older require a documented staged forward migration or read-only diagnostic/export route. At M release, publish the M-1 sunset at the next schema-major release and the migration path. Do not promise indefinite live compatibility. Retirement removes an execution path, not historical evidence: backup/export and required migration tooling remain available for documented supported upgrade paths. Unknown/newer formats open read-only with actionable diagnostics; no automatic reinitialization. Downgrade is only promised where tested and where post-upgrade writes can be preserved or explicitly reconciled.

Use the existing JSON persistence behind a core storage port and the C04 publication boundary. Only registered optional bootstrap absence may mean empty (ADR-095); corrupt/inaccessible/newer or required missing records are unavailable/recovery-required, never a fresh empty store. Versioned index/export formats are derived and rebuildable; operational history is not. A previous-major writer must have a tested lossless adapter, and legacy binaries are quiesced before data cutover. Read compatibility does not authorize two incompatible data-directory writers. U0–U8 covers executable, schema and post-write rollback separately.

## C03 — Honest bounded retrieval

The shared response contract carries schema version, instance/scope, relevant graph/evidence revision, permission-filtered selection policy, freshness, completeness, uncertainty and continuation. Model the dimensions independently: completeness `complete | partial | unknown`, freshness `current | stale | unknown`, and result availability `available | unavailable`; a valid empty result is an available zero-record result, not an unavailable/error response. Reasons include limit, permission, source unavailable, awaiting reconciliation and cursor expiry. Only `complete` authorizes “complete for this requested scope,” never complete knowledge of the whole project. Do not disclose protected entity identities through omission counts.

Bound records and serialized context, preserving complete typed records and required provenance. Return known counts or null/unknown; do not require a global count on each query. Cursor continuation is scope/filter/permission/revision-bound. Preserve a snapshot while supported; otherwise return an explicit revision-changed/expired result requiring restart. Never quietly combine revisions or silently lose graph/relationship classes. Unsupported clients fail visibly. CLI and API presentation may differ but must preserve these meanings. AT02/04/06 judge useful evidence and honest limits, not node volume.

**Old scan does not equal stale graph.** Managed MCP/Architect mutations keep affected knowledge current through reconciliation. Preserve current unaffected and reconciled knowledge even if only one full scan ever occurred. Freshness is relative to concrete evidence changes and committed scope coverage, not scan/enrichment age, raw Git dirty status or commits since scan. Known mismatches/withdrawals or unfinished reconciliation affect only their actual scope; missing history/mapping is separately unknown. Optional pending cognition does not make reconciled source facts stale. A missing old scan baseline may limit a scan operation, but does not invalidate later knowledge. The user chooses an inclusive scan after substantial work outside DreamGraph; do not infer such work from time alone. Explicit expiry for transient observations applies only to that evidence kind. See XS21 for the cross-surface regression specification.

Pin logical/materialized snapshots under bounded retention. Cursors bind family version, instance, scope/filter, permission digest, revision vector and expiry; permission change/restart may explicitly expire them. Revalidation before consequential actions uses affected current hashes/revisions, not a mandatory repository-wide reread. Age is display metadata, not an availability/freshness gate. Old clients either preserve these meanings or receive upgrade-required for unsupported operations.

Persist **`last_graph_mutation_at`** with the graph revision and operation receipt at every successful canonical graph-changing commit, including managed MCP/Architect updates, curation and cognitive writes. Publish it atomically with that commit; failed/rolled-back attempts, reads, no-op saves and view/config-only changes do not advance it. A retry returns the original committed timestamp. Use UTC for display/audit and the monotonic revision for ordering, so clock skew cannot create a false freshness sequence.

Expose separate **`last_full_scan_at`** (last known completed inclusive scan) and **`last_source_reconciliation_at`** plus covered scope/revision (latest successful structural reconciliation). Preserve legacy `last_scan_at` semantics through the compatibility adapter; do not relabel an unknown scan kind as a full scan. Missing historical timestamps remain null/unknown, never fabricated from file mtime or migration time. An inclusive scan advances its marker only after its committed coverage boundary; partial scan progress is reported separately. A successful no-delta source reconciliation may advance its observation/coverage marker without pretending a graph mutation occurred.

MCP graph/context/health responses, API/CLI, SDK/Python exports and all eight surfaces consume the same metadata; UI can show compact “Graph updated …” and “Full scan …” with scope/operation detail available. MCP-aware prompts and recommendations must never conclude “Graph is stale” from full-scan age. Mutation time is useful activity evidence, not a blanket freshness certificate: a recent unrelated dream must not hide unresolved source changes elsewhere, and an old mutation time does not make unchanged knowledge stale. Freshness still follows scoped evidence and reconciliation coverage.

## C04 — Commit receipts, idempotency and recovery

Mutations carry instance, operation identity, expected revision, actor/scope and typed delta. The authoritative receipt identifies operation, commit/revision, affected scope and outcome only after durable commit. A retry with the same identity returns the prior committed outcome; the same identity with different inputs fails. Lost reply is not a new operation. Specify idempotency-record retention and expiration before enabling retries; an expired/unknown receipt must lead to reconciliation, not blind re-execution.

For multi-file changes use the existing persistence authority with a documented journal/staging/commit-marker sequence and restart reconciliation. Separate queued/accepted from committed; batch partial success records each committed boundary and remaining work. For databases or external side effects identify the actual transactional boundary, compensating action where feasible, and recovery-required where not. Do not promise universal exactly-once execution or rollback of an irreversible effect. Record a verified outcome separately from a committed action: executing a remediation is not proof it fixed the risk.

Extend the existing journal/barrier, not an independent transaction service. One process owns each resolved instance directory; platform-correct path identity and fixed logical-resource-then-publication lock order prohibit read-lock upgrades and provider/user waits under locks. Stage prior/next bytes or verified references, expected/new revision vector, operation receipt and outbox; replace stores, invalidate caches and durably publish the commit marker. Before marker recover the predecessor; after marker validate/finish the committed generation and return its receipt. Scan state is a participant, not the universal commit marker. Marker ambiguity fences writes as recovery-required; cleanup failure cannot undo a proven commit. Qualify filesystem/process-crash durability explicitly rather than promising arbitrary hardware recovery.

Operation identity binds actor/scope, epoch, key and payload digest. Terminal unreferenced receipts default to 30-day retention, configurable; pending/unknown effects, unresolved spend and referenced verification/migration evidence stay retained. Retiring an epoch keeps a rejection watermark: an expired key requires reconciliation, never silent new execution. Capacity exhaustion blocks affected admission rather than dropping history. Source/external effects have a durable pre-effect intent and independent post-effect observation; publication of graph/dirty obligations is atomic even though source and graph are not one transaction.

Graph currency metadata is part of the same commit/receipt as its graph delta: C03’s `last_graph_mutation_at` cannot advance before publication or change on replay. Source-reconciliation and inclusive-scan coverage timestamps are distinct; migration cannot manufacture historical values.

## C05 — Job ownership, reservations and hard admission limits

Every job has an owner, instance, operation/config/graph revisions, explicit daemon-durable or session-bound lifetime, cancellation/checkpoint policy and resource budget. Durable jobs survive tab close/refresh and can be reconstructed after reconnect. Distinguish queued, blocked, running, cancelling, cancelled, partial, succeeded, failed and recovery-required, reusing existing state types where possible. Success is decided from committed results, not generated output. A cancellation request stops new admission; outstanding calls may complete and must still be accounted for.

Paid activity requires numeric per-run and per-day limits, currency, a pricing source/version and a declared model/data scope. Unset or zero allocation admits no paid requests. Persist reservations and spend at the shared authority, across restart and concurrent clients. Reserve a conservative maximum before each provider call, including input/context, output/reasoning allowance, retry and concurrent work; reconcile observed usage afterwards. Unknown price or an unbounded request is denied under a hard monetary policy. Reserve retries separately. Outstanding uncertain charges retain a conservative reservation until reconciled. Do not reset usage through retries, schedule duplication, profile changes or daemon restart.

Use a defined UTC daily window and show both its reset instant and the operator's local time; a job crossing midnight remains subject to its original run cap and current applicable day reservations. Aggregate by instance plus billing principal/provider credential reference (never secret text). If credentials are shared beyond this daemon, state that the bound covers DreamGraph-admitted requests, not unrelated account usage. Provider invoices may differ from estimates; distinguish reserved/estimated/observed usage and final charge, alert and halt new admission on variance instead of claiming exact control of an external bill.

Bound hops, selected neighbors, input tokens, output/reasoning allowance, requests, retries, elapsed time and concurrency independently. A one-hop hub can be expensive. A budget stop preserves completed source scanning and valid enrichment, reports evidence-only/unfinished nodes honestly, and supports targeted continuation. Each result/checkpoint records effective configuration; a profile change is not retrospective enrichment. Do not weaken automatic-dream completeness/readiness requirements to make partial enrichment look successful.

Core job/attempt records are introduced in 5/6; scheduler 17 schedules them. Separate operation, job, execution attempt/fence, session, discipline history and schedule occurrence. ADR-239 owns one typed terminal cancellation/deadline cause. Record cancellation and fence before further dispatch; committed effects remain committed, late provider results settle usage but cannot silently commit new cancelled work. A Promise.race timeout is not stop proof: retain conflict capacity until acknowledgement, isolated-worker termination or effective fencing, otherwise recovery-required.

Every provider dispatch uses this admission seam, including readiness probes, fingerprint bootstrap, narrative/future review, evaluation and plugins. Configured is not verified-ready; unfunded probes remain unverified/budget-blocked. Fingerprint changes cannot authorize spending. Calls retain their UTC admission-day reservation across midnight; new calls reserve the new day and the same run allocation. If multiple instances share an allocated budget, assign fixed child allocations whose sum fits it; a per-instance cap never claims to control unrelated account use. Initial mutating cognition is serialized per instance; unrelated readers and independently scoped work stay concurrent.

## C06 — Role policies, API/CLI capabilities and retention

Initial scan, targeted enrichment, dreamer, normalizer and Architect have independent saved policies. GPT-4.1 and GPT-5.4 remain examples or user preferences, not permanent defaults or ceilings. A profile chooses model/adapter/API/effort/context/output/retries/timeouts/allowed fallbacks and spend; it does not redefine completeness or evidence requirements. Preview requested and resolved provider/model, execution transport, effort, hops and limits before expensive work. Preserve supported custom models/endpoints with explicit validated capability overrides and provenance; model names alone cannot prove capabilities.

Reuse current provider adapters, including Responses, and preserve native API continuation separately from CLI execution. Unsupported parameters produce actionable feedback rather than silent removal. Retain host-side schema validation even when a provider offers structured output. Report refusal, incomplete output, fallback reason and changed guarantees explicitly. Never silently switch to a stronger/more expensive model or weaker schema/evidence contract. CLI subscription consumption is unknown/adapter-reported unless actually measured; API tariffs must not be presented as actual subscription charges. Apply request/token/time limits where monetary attribution is unavailable, and do not label that a verified currency cap.

Provider storage/retention is a separate setting from evaluation mode or access level. Show supported request controls, effective policy and provider/account limits; a client flag alone is not a zero-retention guarantee. Declare exactly which source/evidence is sent and sanitize traces/artifacts. A real-model canary requires credentials, approved data/model scope, run/day allocation and explicit opt-in. Normal CI stays offline and cannot acquire a paid grant from a template or environment default.

Configured role policy and its allowed overrides take precedence over implicit connected-model reuse (proposed scoped ADR-203 amendment). Provider readiness (ADR-098) is separately admitted under C05. Declare deterministic fallback explicitly; it cannot fulfill a missing mandatory LLM/vision/evidence capability. Preserve ADR-240: neutral execution requirements and task targets cross adapters, API continuation envelopes never enter native CLI control, and an intermediate completed slice does not itself terminate an authorized multi-slice task. Early API/CLI/CU-schema fixtures are not real native interaction qualification; 31/27 close those obligations.

## C09 — Local authority and scoped full-access mode

Local-only is the default. Remote binding requires explicit enabling, authentication, authorized origins/hosts and visible remote/bind status in UI/CLI. Loopback is not a substitute for browser origin/session checks. Clients reconstruct state from the daemon; cached badges or a selected tab never confer execution authority.

Full access is an explicit scope expansion available through **two independent human confirmations**. First present a precise scope/data/actions/providers/models/budget/retention/expiry preview. Then require a fresh confirmation of the same immutable proposal digest before issuing a short-lived server-side grant. No prechecked confirmation, automated second confirmation or generic persistent “yes to everything.” Bind the grant to principal, instance, operation/scope and policy revision; expire at task end or a configured finite timeout, and provide immediate revoke. Expansion or changed terms invalidates the prior confirmation. It is not enabled by template import, reconnect, saved chat or ordinary CI.

This reconciles full access with explicit caps: the user may raise limits or broaden declared scope through that flow, but the new finite run/day allocations are still enforced. Full access does not bypass truth/promotion, commit/recovery, audit or authentication rules; it does not enable remote access or change provider retention implicitly. This is a product behavior requirement, not a request for two confirmations now. The audit/planning work requires no such grant.

Sessionless protected commands cannot inherit a process-wide discipline session. The extension host owns its transcript/editor view; daemon owns execution/graph state. ## C11 — Rebuild schedule management around the existing scheduler

The dashboard schedule page is a full workflow rebuild; `src/cognitive/scheduler.ts` remains the owner. Source inspection found create/toggle/run/delete forms but no edit workflow, raw millisecond fields, no cron next-run forecast, historical strategy labels derived from current schedule parameters, and invalid action parameters falling back to defaults. The latter can broaden intended work and must be handled in the scheduler contract, not patched only in forms. These are source observations; no live schedule was mutated or executed during refinement.

Use a compact list with search/filter (enabled, paused, blocked, error, action, next occurrence), multi-select only for bounded reviewed operations, and an inspector/editor. Tabs: Schedules, Upcoming, Runs; details show Definition, Effective policy and History. Support create, edit, duplicate, enable/pause, run now, cancel a run, and archive/delete with retained execution evidence. Use explicit set-enabled operations with expected revisions, not race-prone toggles. Schedule ID is stable; edits increment definition revision; duplicate creates a new ID and starts disabled. New schedules are saved disabled until the enable preview is accepted. Existing enabled schedules keep their documented migration disposition, never silently reschedule on opening the UI.

The editor uses human time units and action-specific fields generated/validated from core schemas. Show scope/focus entities, strategy, role/profile, requested/resolved model, context limits, retries, run/day allocation and estimated maximum per occurrence. Undefined or invalid parameters block with field errors; they must not fall back silently to a broader action/default. A read-only preview reports effective policy and next five clock occurrences, or accurately states that cycle/idle timing depends on future activity. Validation/preview must never call a model or enqueue work.

Trigger policy is explicit: interval cadence uses duration/elapsed semantics with persisted due instants; cron/calendar intent has a named timezone. Preserve existing UTC cron intent during migration; do not reinterpret it as local time. Initially supported cron syntax must be declared and rejected outside that grammar, not silently misparsed. Add named-zone calendar scheduling with a documented DST rule: skipped local time is logged as missed/skipped by default; repeated local wall time runs once unless a reviewed policy explicitly requests both. Preview and execution use the same evaluator. Display timezone and next occurrence in both its configured zone and local operator time (Europe/Helsinki here), with UTC audit timestamps. Cycle and idle triggers retain their distinct engine semantics.

Default missed-run policy is skip with reason, consistent with current scheduler intent; optional catch-up-once coalesces missed occurrences rather than replaying an unbounded backlog. Default overlap is one active run per schedule; skip/defer is explicit and any queue is bounded. Global engine locks and budgets still apply across different schedules/manual jobs. Restart reconciles run leases/checkpoints before dispatch and prevents duplicate occurrences. “Run now” submits a job through the same authorization/readiness/budget admission; it does not bypass guards. Pausing affects future dispatch; cancelling the active job is a separate visible action. Deleting/archiving a definition does not erase history or silently cancel unrelated work.

Every run snapshots definition revision, actual action/strategy/scope, requested/resolved model and adapter, effective config/pricing/retention policy, planned occurrence, actual start/end, skip/block reason, reservations/usage, cancellation and commit/result references. Historical display uses that snapshot, not today's definition. Unknown legacy run details remain unknown. Show queued/running/blocked/partial/recovery states and actionable reasons, not just ok/fail. SSE/poll reconnection reconstructs state from the daemon; UI selection never owns the job.
